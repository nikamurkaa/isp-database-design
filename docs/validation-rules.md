# Правила валидации и целостности данных

Документ фиксирует проверки, которые заложены в проектирование БД и должны дополняться проверками на уровне приложения/API.

## Клиенты

| Поле | Правило | Поддержка в БД |
| --- | --- | --- |
| Тип клиента | Только `individual` или `legal_entity`. | `CHECK` на `clients.client_type`. |
| Телефон | Обязателен и уникален. | `NOT NULL`, `UNIQUE`. |
| Логин | Обязателен и уникален. | `NOT NULL`, `UNIQUE`. |
| Email | Необязателен, но уникален при наличии. | `UNIQUE`. |
| Имя/фамилия физлица | Обязательны для физического лица. | `CHECK` в `clients`. |
| Серия паспорта | 4 цифры в публичной демо‑схеме. | Regex `CHECK`. |
| Номер паспорта | 6 цифр в публичной демо‑схеме. | Regex `CHECK`. |
| Полное название юрлица | Обязательно и уникально. | `NOT NULL`, `UNIQUE`. |
| ОКПО | 8 или 10 цифр. | Regex `CHECK`. |
| БИК | 9 цифр. | Regex `CHECK`. |

## Каталог

| Поле | Правило | Поддержка в БД |
| --- | --- | --- |
| Артикул оборудования | Обязателен и уникален. | `NOT NULL`, `UNIQUE`, regex `CHECK`. |
| Артикул услуги | Обязателен и уникален. | `NOT NULL`, `UNIQUE`, regex `CHECK`. |
| Цена | Не может быть отрицательной. | `CHECK`. |
| Пропускная способность | Положительное значение при наличии. | `CHECK`. |
| Бренд + модель | Модель уникальна внутри бренда. | Составной `UNIQUE`. |
| Характеристики оборудования | Одна характеристика одного типа на единицу оборудования. | Составной `UNIQUE`. |

## Договоры

| Поле | Правило | Поддержка в БД |
| --- | --- | --- |
| Номер договора | Обязателен и уникален. | `NOT NULL`, `UNIQUE`, regex `CHECK`. |
| День оплаты | Диапазон 1–28. | `CHECK`. |
| Денежные поля | Не могут быть отрицательными. | `CHECK`. |
| Статус договора | Только разрешённые статусы. | `CHECK`. |
| Клиент договора | Должен ссылаться на существующего клиента. | Foreign key. |
| Сотрудник договора | Должен ссылаться на существующего сотрудника. | Foreign key. |
| Позиции договора | Количество больше нуля. | `CHECK`. |

## Платежи

| Поле | Правило | Поддержка в БД |
| --- | --- | --- |
| Номер операции | Обязателен и уникален. | `NOT NULL`, `UNIQUE`. |
| Тип операции | Только известные типы операций. | `CHECK`. |
| Начисленная сумма | Неотрицательная. | `CHECK`. |
| Оплаченная сумма | Неотрицательная и не больше начисленной. | `CHECK`. |
| Договор | Ссылка на существующий договор. | Foreign key. |

## Заявки и технические задачи

| Поле | Правило | Поддержка в БД |
| --- | --- | --- |
| Адрес подключения | Обязателен. | `NOT NULL`. |
| Запрошенная скорость | Положительная при наличии. | `CHECK`. |
| Статус заявки | Только разрешённые значения. | `CHECK`. |
| Статус задачи | Только разрешённые значения. | `CHECK`. |
| Приоритет задачи | Только разрешённые значения. | `CHECK`. |
| Время решения | Не раньше времени создания задачи. | `CHECK`. |

## Проверки уровня приложения

Часть правил лучше реализовывать на уровне backend/API:

- человекочитаемые ошибки для форм;
- маски и нормализация телефонных номеров;
- проверка формата email;
- требования к сложности пароля и безопасное хеширование;
- Luhn‑проверка банковских карт, если когда‑либо потребуется хранить полные номера;
- детальная авторизация, например доступ клиента только к собственным договорам;
- бизнес‑процессы согласования мощности сети и закрытия технических задач.
