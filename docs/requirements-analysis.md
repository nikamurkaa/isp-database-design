# Анализ требований

## Бизнес-контекст

Проект моделирует информационную систему интернет‑провайдера. Провайдер подключает клиентов к интернету, продаёт или сдаёт оборудование, оказывает дополнительные услуги, обрабатывает технические заявки и ведёт платежи по договорам.

В публичной версии репозитория три учебных направления объединены в один инженерный кейс:

1. **Анализ и проектирование баз данных** — анализ предметной области, сущности, атрибуты, нормализация, ERD и словарь данных.
2. **СУБД PostgreSQL / MySQL** — физическая схема, SQL‑скрипты, роли доступа, представления, функции, процедуры и запросы.
3. **Сборка полнофункциональных приложений** — группы пользователей, функции системы, архитектура, модули, правила валидации и контроль целостности.

## Цели системы

Система должна помогать интернет‑провайдеру:

- вести каталог услуг и оборудования;
- регистрировать физических и юридических лиц;
- принимать и обрабатывать заявки на подключение;
- оформлять договоры на услуги и оборудование;
- учитывать монтажные работы и технические обращения;
- фиксировать платежные операции;
- хранить информацию о доступной сетевой мощности;
- разделять права доступа между администраторами, менеджерами, техническими специалистами и клиентами.

## Пользователи и зоны ответственности

| Группа пользователей | Ответственность |
| --- | --- |
| Клиент | Оставляет заявки, просматривает услуги, договоры, платежи и обращения в поддержку. |
| Менеджер по клиентам | Регистрирует клиентов, проверяет данные, оформляет договоры и платежи. |
| Специалист технической поддержки | Выполняет задачи подключения, монтажа и обработки технических обращений. |
| Главный технический специалист | Управляет каталогом услуг/оборудования и обновляет сведения о доступной мощности сети. |
| Администратор | Управляет сотрудниками, ролями, правами доступа и справочниками. |

## Функциональные требования

### Каталог услуг и оборудования

- Хранить интернет‑услуги, дополнительные услуги и стоимость подключения/ежемесячной оплаты.
- Хранить типы оборудования, бренды, модели, пропускную способность и характеристики.
- Поддерживать поиск по артикулу, названию, типу оборудования, бренду и модели.
- Не удалять исторически использованные позиции каталога: для этого предусмотрен флаг активности.

### Управление клиентами

- Поддерживать два типа клиентов: физическое лицо и юридическое лицо.
- Хранить общие контактные и учётные данные в таблице `clients`.
- Хранить паспортные/регистрационные данные физлиц отдельно.
- Хранить регистрационные и контактные данные юрлиц отдельно.
- Контролировать уникальность логина, телефона, email и регистрационных идентификаторов.

### Договоры

- Создавать договор с уникальным номером, датой оформления, клиентом, менеджером, сроком оплаты и статусом.
- Привязывать к договору несколько услуг и единиц оборудования.
- Сохранять исторические цены в деталях договора, чтобы изменения каталога не переписывали старые договоры.
- Учитывать стоимость работ, оборудования и ежемесячный платеж.

### Платежи

- Регистрировать платежные операции по договору.
- Разделять типы операций: монтажные работы, ежемесячный платеж, покупка оборудования, возврат.
- Хранить начисленную сумму, оплаченную сумму, дату, время и комментарий.
- Формировать отчёт по начислениям, оплатам и задолженности.

### Заявки и техническая поддержка

- Позволять клиенту оставить заявку на подключение услуги.
- Хранить адрес подключения и требуемую пропускную способность.
- Проверять текущую доступную мощность сети.
- Создавать технические задачи на подключение или обслуживание.
- Назначать задачи специалистам поддержки.
- Отслеживать статус, приоритет, оборудование и время решения обращения.

### Управление сетевыми ресурсами

- Хранить снимки доступной сетевой мощности.
- Учитывать доступную пропускную способность и количество оборудования.
- Использовать последний снимок мощности для проверки возможности подключения.

## Нефункциональные требования

| Область | Требование |
| --- | --- |
| Целостность данных | Использовать первичные и внешние ключи, уникальные ограничения и `CHECK`. |
| Безопасность | Разделять права доступа и не публиковать реальные персональные данные. |
| Поддерживаемость | Разделить SQL‑скрипты по зонам ответственности: схема, данные, индексы, views, functions, procedures, permissions. |
| Переносимость | Основная реализация — PostgreSQL; дополнительно приложена MySQL‑совместимая схема. |
| Документация | Описать модель данных, архитектуру, правила валидации и процесс очистки учебных материалов. |
