# Гид для быстрого просмотра проекта

Этот документ помогает быстро понять ценность репозитория без чтения всех файлов подряд.

## 1. Сначала посмотрите README

`README.md` объясняет идею проекта, предметную область, структуру репозитория, запуск PostgreSQL, ERD и архитектуру.

## 2. Затем откройте основную схему БД

Файл: [`sql/postgresql/01_schema.sql`](../sql/postgresql/01_schema.sql)

Что важно увидеть:

- 19 нормализованных таблиц;
- связи через внешние ключи;
- ограничения `CHECK`, `UNIQUE`, `NOT NULL`;
- разделение клиентов на физических и юридических лиц;
- детализацию договоров через отдельные таблицы услуг и оборудования;
- сохранение платежных операций и технических задач.

## 3. Посмотрите SQL‑объекты PostgreSQL

| Файл | Что показывает |

| [`03_indexes.sql`](../sql/postgresql/03_indexes.sql) | Индексы для поиска, связей и отчётов. |

## 4. Оцените проектирование

Файлы:

- [`docs/database-design.md`](database-design.md) — нормализация и проектные решения;
- [`docs/data-dictionary.md`](data-dictionary.md) — словарь данных;
- [`docs/validation-rules.md`](validation-rules.md) — правила валидации и целостности.

## 5. Оцените системное мышление

Файл: [`docs/system-architecture.md`](system-architecture.md)

Он показывает, как БД встраивается в более широкую систему: desktop, web, mobile клиенты, API Gateway, доменные сервисы, PostgreSQL и notifications.

## 6. Что демонстрирует проект

- Понимание реляционного проектирования.
- Практический SQL, а не только диаграммы.
- Умение документировать технические решения.
- Внимание к целостности данных и безопасности публикации.
- Способность привести учебные материалы к профессиональному portfolio‑формату.

## 7. Ограничения проекта

Проект не заявлен как production‑готовый SaaS или backend API. Это database/system design case study. Для production‑уровня потребовались бы backend‑сервис, полноценная авторизация на уровне приложения, миграции, тесты SQL‑скриптов в CI и row‑level security для клиентских сценариев.
